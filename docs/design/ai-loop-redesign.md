# uiai 再設計案: AI を毎ステップ挟む実行方式（コンパイル廃止）

- ステータス: 方針決定済み・未着手
- 作成日: 2026-11-12
- 根拠となる試作: `prototype/ai-loop/`（コミット `225da4f`）

## 1. 結論

**プログラムがループを回し、AI には 1 ステップにつき 1 回だけ判断させる。画面の入力はスクリーンショットだけにする。コンパイル（決定的リプレイ）は廃止する。**

- AI の判断は 1 回あたり約 1 秒で、ボトルネックではない。
- 画像だけで、タップ位置・状態の判定・割り込み処理・一字一句の文字確認まで実用的にこなせた。
- 画面取得は、スクリーンショットなら Android 約 0.15 秒、Web 約 0.02 秒で、UI ツリー（`uiautomator dump` は 2〜30 秒、画面によっては取得できない）より速く安定している。
- プラットフォームごとの差は「撮る・押す・打つ」などの小さな部品だけに閉じ込められる。Web 版は、この部品を差し替えるだけで動いた。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 既定のモデル | haiku |
| スキルの形 | `/uiai:test` 1 つに統合（`platform` 引数、省略時は自動判定） |
| 配布と依存 | プラグインの `bin/` に起動スクリプトを置き、エンジンの依存は uv で自動導入する |
| strict（厳密な判定） | AI による画像判定（一字一句の完全一致）。AI が読み取った文字をレポートに残す |
| 失敗したとき | 最後まで走らせる。失敗はリアルタイムに通知する |
| iOS | Mac とシミュレータに限定する。Windows・Linux からの iOS 操作は後から足せる作りにする |

## 3. 現行方式の問題

| 問題 | 内容 |
|---|---|
| 遅い | ランナー（サブエージェント）がシナリオ全体を回し、評価エージェントがあとから `then` を判定する。画面取得の `uiautomator dump` は 1 回 2〜3 秒かかり、30 秒止まることや失敗することもある |
| 不確定要素に弱い | コンパイル結果は「前回と同じ画面が出る」前提で動く。トースト・予期しないダイアログ・読み込み時間の揺れに弱い |
| 対応の偏り | コンパイルは Android のみ。iOS/Web は未対応 |
| 抜け | `ai_required` と判定された `do` は実行されない |

## 4. 計測結果（根拠）

いずれも Claude Code（`claude -p` の持続セッション、stream-json）経由で計測した。各条件の実行は 1〜2 回で、統計的な裏付けとしては少ない。

### 4.1 通しの実行

| 対象 | 画面の取り方 | モデル | 合計 | 1 ステップ | AI 1 回 | 判定 |
|---|---|---|---|---|---|---|
| Android 設定アプリ（`do` 9） | UI ツリー（`adb` dump） | sonnet | 111.8 秒 | 12.4 秒 | 1.83 秒 | 5/6 |
| 同上 | UI ツリー（uiautomator2） | sonnet | 49.5 秒 | 5.5 秒 | 2.02 秒 | 6/6 |
| 同上 | **画像のみ** | sonnet ×3 | 46.0〜50.0 秒 | 5.1〜5.6 秒 | 1.09〜1.22 秒 | 6/6 ×3 |
| 同上 | **画像のみ** | haiku ×2 | 47.6〜51.2 秒 | 5.3〜5.7 秒 | 1.21〜1.27 秒 | 6/6 ×2 |
| Web 試験アプリ（`do` 11） | **画像のみ** | sonnet ×2 | 27.8〜30.9 秒 | 2.5〜2.8 秒 | 0.96〜1.04 秒 | 8/8 ×2 |
| 同上 | **画像のみ** | haiku ×2 | 33.0〜34.1 秒 | 3.0〜3.1 秒 | 0.93〜0.94 秒 | 8/8 ×2 |
| Wikipedia（実サイト、`do` 3） | **画像のみ** | sonnet/haiku ×2 ずつ | 14.0〜17.3 秒 | 4.7〜5.8 秒 | 0.98〜1.16 秒 | 3/3 ×4 |

- Android の画像方式の時間は、約半分がアプリ自身のアニメーションや読み込みの待ち（撮影自体は 0.15 秒）、約 4 割が AI。
- Web は撮影が速いため、約 7 割が AI。
- 判定の正しさは、AI に送った画像と突き合わせて確認した。確認したのは抜き取りで、画像のみ方式の Android（sonnet・haiku 各 1 本）、Web 試験アプリ（haiku 1 本）、Wikipedia（haiku 1 本）。UI ツリー方式の 6/6 は画像では確認していない。

### 4.2 Web 試験アプリで確かめた不確定要素

| 要素 | 結果 |
|---|---|
| 3 秒で消えるトースト | 操作直後の静止画面で捉えて判定できた |
| シナリオに書いていない Cookie 同意ダイアログ | AI が割り込みとして閉じて続行した |
| 保存前の確認ダイアログ | 取り直しの中で「保存する」を押し、判定し直した |
| 2 秒かかる検索（読み込み表示あり） | 取り直しで待ってから合格した |
| 日本語入力 | Web は問題なし。Android の `adb input text` は日本語非対応（未対応） |

### 4.3 画像だけでのタップ精度（Android、座標だけを答えさせる試験）

| 画面 | sonnet | haiku |
|---|---|---|
| 設定アプリの各項目・スイッチ・戻る矢印 | 7/7 | 7/7 |
| 言語一覧の末尾（日本語・简体中文・繁體中文・粵語・한국어） | 5/5 | 5/5 |
| ホーム画面の小アイコン（126px 角） | 5/5 | 5/5 |
| クイック設定の小アイコン（126px 角） | 5/5 | 5/5 |
| キーボード（入力欄が「kem」になるかで判定） | 5/5 | 5/5 |

1 回の応答は sonnet 約 0.9〜1.2 秒、haiku 約 0.7 秒。試した中で一番小さい対象は 126px 角（48dp 相当）。

### 4.4 画像だけでの厳密な文字判定（strict の根拠）

| 試験 | haiku | sonnet |
|---|---|---|
| Web: 紛らわしい表記の判定（正しい表記 8 問・紛らわしい別表記 8 問） | 14/16 | 14/16 |
| └ 紛らわしい別表記を「不一致」と見抜けたか | 8/8 | 8/8 |
| └ 正しい表記を「一致」と認めたか | 6/8 | 6/8 |
| Android 端末情報画面の 5 項目（15 桁の IMEI を含む）の書き起こし（540×1200 / 1080×2400） | 5/5 / 5/5 | 5/5 / 5/5 |

- 見分けられた: 「本社」と「本店」、英字 O と数字 0、小文字 l と数字 1 と大文字 I、長音記号「ー」とハイフン、全角英字、11px の小さい文字。
- 間違えた 2 問は、画面上の見た目ではほぼ区別できない文字だった（半角「¥」を全角「￥」と読んだ、半角スペース 2 つを全角スペース 1 つと読んだ）。どちらも「一致しているのに不一致」とした安全側の誤りで、紛らわしい別表記を誤って合格にしたことはない。
- 同じ試験中、Android の端末情報画面では `uiautomator dump` が「could not get idle state」で毎回失敗した。UI ツリーで照合する方式は、画面によってはそもそも動かない。

### 4.5 部品ごとの速さ

| 処理 | 時間 |
|---|---|
| Android `uiautomator dump` | 2.0〜3.3 秒（最大 30 秒、静止しない画面では取得できない） |
| Android uiautomator2（常駐） | 0.04 秒。ただし操作直後は古い画面を返す。`adb` の dump と同時に使えない |
| Android スクリーンショット（raw） | 0.15 秒 |
| Web スクリーンショット | 0.02 秒 |
| AI 1 回（画像あり・返答 約 75 トークン） | 0.9〜1.3 秒 |
| AI 1 回（UI ツリー文字列） | 約 2.0 秒（画像より遅い理由は未確認） |

## 5. 設計方針

1. **プログラムがループを回し、AI は判断だけ**: `do` 1 つにつき AI を 1 回呼ぶ。その 1 回で「前の `then` の判定」と「次の操作」を同時に返させる。
2. **画面の入力はスクリーンショットだけ**: UI ツリーは使わない（取得が遅く、画面によっては取れないため）。
3. **`then` は「落ち着いた画面で満たされるか」で判定**: 不合格ならすぐ失敗にせず、待って取り直す。割り込みを片付ける操作も挟める。
4. **プラットフォーム差は小さな部品（ドライバ）に閉じ込める**: ループ・AI・レポート・通知は全プラットフォーム共通。
5. **決定的リプレイ（コンパイル）は持たない**: 毎回 AI が画面を見て判断する。
6. **すべての判断を証拠付きで残す**: 各呼び出しの画像・操作位置・AI の理由・読み取った文字をレポートに残し、あとから人が確かめられるようにする。
7. **失敗しても最後まで走らせ、失敗はその場で知らせる**。

## 6. プラグイン構成と動作環境

### 6.1 構成

```
uiai/
├── .claude-plugin/plugin.json
├── bin/
│   ├── uiai              # mac・Linux・Windows（Git Bash）用の起動スクリプト
│   └── uiai.cmd          # Windows（PowerShell）用
├── engine/
│   ├── main.py           # 依存ライブラリをファイル先頭に宣言（PEP 723）。uv run --script で起動
│   └── uiai/
│       ├── cli.py        # uiai run / check / setup / watch
│       ├── scenario.py   # YAML 読込・変数・プレースホルダー・replay 展開・検査
│       ├── loop.py       # ステップ実行・then 判定・取り直し・割り込み・失敗時の続行
│       ├── settle.py     # 画面の「変化待ち → 静止待ち」
│       ├── ai/claude_code.py   # 既定: claude -p の持続セッション
│       ├── ai/api.py           # 任意: ANTHROPIC_API_KEY で直接呼ぶ
│       ├── drivers/{base,android,ios,web}.py
│       ├── events.py     # 失敗などのイベント出力（stdout と events.jsonl）
│       ├── notify.py     # Webhook など
│       └── report.py
├── skills/test/SKILL.md            # /uiai:test
└── skills/scenario-check/ ほか（11 章）
```

- `bin/` に置いたファイルは、プラグインが有効な間、Claude が実行するシェルの PATH に入る（公式仕様）。スキルからは `uiai run ...` とだけ書けばよい。
- 前提は uv だけ。uv は mac・Linux・Windows で動き、Python 本体と依存ライブラリ（画像処理・YAML・Playwright など）を自動で用意する。Playwright 用のブラウザは初回に `uiai setup` で取得する。
- プラグイン用の保存場所 `${CLAUDE_PLUGIN_DATA}` は、スキルから実行するコマンドには渡されない（公式仕様）。依存の管理は uv のキャッシュに任せる。
- Node.js は前提にしない（Claude Code のネイティブ版は Node.js なしで動くため）。

### 6.2 OS ごとの対応

| | mac | Linux | Windows |
|---|---|---|---|
| Android（adb） | ○ | ○ | ○ |
| Web（Playwright） | ○ | ○ | ○ |
| iOS シミュレータ（Xcode と idb） | ○ | × | × |

Windows での実装上の注意:

- 日本語版 Windows は文字コードの既定が UTF-8 ではない。Claude Code とのやり取り・ファイル入出力は UTF-8 を明示する（試作のままでは日本語が化ける）。
- `claude` の実体は `.exe` か `.cmd` かでばらつくため、実行ファイルの探し方を分けて扱う。
- Claude Code は、Git Bash がなければ PowerShell でコマンドを実行する。`bin/uiai.cmd` が PowerShell から PATH 経由で呼べるかは未検証。

### 6.3 iOS を Windows・Linux から動かす道（後から足す）

iOS シミュレータは Xcode の一部で、macOS でしか動かない。Windows・Linux から動かす道はあるが、どれも Apple 側の何かが要る。

| 方法 | 必要なもの | 評価 |
|---|---|---|
| ① 別の Mac を遠隔操作 | Mac と Xcode がどこかに 1 台。Windows・Linux 側は idb の操作側ソフトだけ（Mac 側の常駐ソフトとネットワーク越しに通信） | 一番現実的 |
| ② 実機の iPhone を USB で直接つなぐ | 撮影は pymobiledevice3 や go-ios で可能。タップと文字入力には、iPhone 上の WebDriverAgent が必要（Apple の開発者署名付きで、最初の 1 回は Mac の Xcode でビルド） | iOS 17 以降は「実験的」扱いで、手順が重く不安定（未検証） |
| ③ クラウドの実機サービス | Mac 不要。有料 | 予算があれば一番手軽 |

iOS ドライバは、撮影・タップ・入力の担当部分（idb をローカルで使う／idb を遠隔で使う／WebDriverAgent の HTTP を使う）を差し替えられる作りにする。

## 7. ドライバ（プラットフォーム部品）

AI が返す座標は「送った画像上の座標」。ドライバが実機の座標に換算する。

| 操作 | Android | iOS シミュレータ（未検証） | Web |
|---|---|---|---|
| 撮影 | `adb exec-out screencap`（raw） | `xcrun simctl io booted screenshot` | `page.screenshot()` |
| タップ | `input tap` | `idb ui tap` | `mouse.click` |
| 文字入力 | `input text`（ASCII のみ。日本語は ADB Keyboard 等が必要、未検証） | `idb ui text` | `keyboard.type` |
| キー | `input keyevent` | `idb ui key` | `keyboard.press` |
| スクロール | `input swipe` | `idb ui swipe` | `mouse.wheel` |
| 戻る | `keyevent 4` | なし（AI が戻るボタンを押す） | `go_back` |
| 起動 | `monkey -p` | `simctl launch` | `goto` |
| 初期化 | `force-stop`（＋関連パッケージ、任意で `pm clear`） | `simctl terminate` | 新しいブラウザコンテキスト |

## 8. 実行ループ

```
for each section:
  for each do:
    attempts = 0
    while attempts < max_attempts:          # 既定 5
        screen = settle(driver)             # 変化待ち（最大 2 秒）→ 0.1 秒間隔で 2 回連続ほぼ同じ
        reply  = ai.ask(do, pending_thens, screen, history)
        if pending_thens に不合格がある and 取り直し回数 < 上限:   # 既定 2 回
            if reply.interrupt and reply.action が具体的な操作:
                driver.act(reply.action)    # 例: 確認ダイアログの「保存する」
            else:
                sleep(1)
            continue                        # 判定を確定させずに取り直す
        判定を確定（不合格なら失敗イベントを出す）→ pending_thens を空に
        driver.act(reply.action)
        attempts += 1
        if reply.done: break
    if do が実行できなかった:
        失敗イベントを出し、このセクションの残りを飛ばして次のセクションへ
```

- **`then` の判定タイミング**: 直前の `do` の操作が終わり、画面が落ち着いた最初の画像で判定する。トーストはここで捉える。
- **画面の落ち着き判定**: 操作直後は、まず画面が変わるのを待ち（小さな変化も拾う）、そのあと静止を待つ（文字カーソルの点滅は許容し、回転する読み込み表示は許容しない）。Android はステータスバーを比較から外す。
- **割り込み**: シナリオにないダイアログは AI が片付け、レポートに「割り込み」として残す。`config.interrupts` で扱いを選べる（`allow`: 片付けて続行／`report`: 続行して警告／`fail`: 失敗にする）。
- **失敗したとき（決定）**: 止めずに最後まで走らせる。
  - `then` が不合格 → 記録して次のステップへ。
  - `do` が実行できない（AI が `fail` を返す、または試行回数を超える）→ そのセクション（`steps[].id`）の残りを飛ばし、次のセクションへ。想定外の画面のまま操作を続けても意味のない結果になるため。
  - `config.on_failure: stop` を指定したときだけ、最初の失敗でシナリオを打ち切る。

## 9. 失敗のリアルタイム通知

エンジンは、失敗のたびに 1 行のイベントを出す。内容はシナリオ名・セクション・ステップ・期待結果・AI の理由・AI が読み取った文字・画像のパス。出力先は標準出力と `.uiai/results/<timestamp>/events.jsonl`。

| 経路 | 届く先 | 用途 |
|---|---|---|
| Claude Code のセッション（標準） | チャット。席を離れていれば、デスクトップ通知（Remote Control 接続中はスマホにも） | ふだんの実行 |
| Webhook（任意） | Slack・Teams など。URL は環境変数 `UIAI_WEBHOOK_URL` などで渡す | CI や、Claude Code を使わずに実行するとき |
| OS のデスクトップ通知（任意、後回し） | mac・Linux・Windows の通知センター | Claude Code なしで手元で実行するとき |

Claude Code のセッションでの流れ:

1. `/uiai:test` のスキルは、`uiai run` をバックグラウンドで起動する（実行中も会話を止めないため）。
2. 続けて `uiai watch --run <id>` を Monitor ツールで見張る。`watch` は失敗イベントだけを 1 行ずつ出し、実行が終わると終了する。
3. 失敗が届くたびに、Claude がチャットで知らせる。ユーザーが席を離れていそうなら、デスクトップ通知（PushNotification）も送る。
4. 実行が終わったら、レポートを要約して返す。

プラグインの「モニター」機能（`monitors.json` の `when: "on-skill-invoke:test"`）でも同じことができるが、仕様が experimental 扱いのため、まずは Monitor ツールを使う。なお、どちらも非対話モード（`claude -p`）では動かないため、CI での通知は Webhook に任せる。

## 10. AI の呼び出し

- **既定は Claude Code バックエンド**: `claude -p` を 1 プロセス起動したまま、stream-json でメッセージを送る。API キーが要らず、ユーザーの Claude Code の認証で動く。ツール無効・ユーザーのフック無効（`--tools ""`、`--setting-sources project` など）で起動する。
- **既定のモデルは haiku（決定）**。`config.model` やコマンドの引数で変えられる。計測では haiku と sonnet で判定精度の差はなかった。
- **会話が長くなる問題**: 画像は 1 枚 1,000〜1,400 トークンで、25 回の呼び出しで約 4 万トークンになった。対策として、セクション（`steps[].id`）ごとにセッションを作り直し、それまでの操作履歴はテキストで引き継ぐ。セッション起動にかかる時間は未計測。
- **任意で API バックエンド**: `ANTHROPIC_API_KEY` があれば、毎回の入力を自分で組み立てる（最新の画像 1〜2 枚＋テキストの履歴）。会話が伸びず、プロンプトキャッシュも効く。
- **呼び出し回数を減らす**: 「入力欄をタップ」と「文字を打つ」を 1 回の `input` にまとめるようプロンプトで促す。試作の Web 試験アプリでは、AI が自分からまとめた実行は 19 回・27.8 秒、分けた実行は 23 回・30.9 秒だった（プロンプトで促した場合の効果は未検証）。
- **改善案（未検証）**: `then` の不合格を確定する前だけ sonnet で判定し直し、誤った不合格を減らす。

## 11. シナリオ形式

既存のシナリオはそのまま動くようにする。

| フィールド | 新設計での扱い |
|---|---|
| `name`、`steps`、`id`、`actions`、`do`、`then` | そのまま |
| `app`（`android`/`ios`/`web`） | そのまま。`web` を正式に追加（URL、またはシナリオからの相対パス） |
| `variables`・プレースホルダー | そのまま（エンジンで解決） |
| `replay` | そのまま（エンジンで展開。`then` はスキップ） |
| `wait` | そのまま（固定待機） |
| `strict` | 意味を変更: AI に「一字一句の完全一致」で画像を判定させる。AI が読み取った文字をレポートに残す。見た目で区別できない文字（半角と全角の空白、半角「¥」と全角「￥」など）は判定できないことをドキュメントに明記する |
| `verify`（`uitree`/`ai`/`screenshot`） | 廃止（`uitree` の指紋照合はコンパイル前提のため）。書かれていても警告して無視する |
| `config.timeout`、`clear_data_before`、`stop_app_after` | そのまま（ドライバの初期化・終了処理へ） |
| 新規 `then.timeout` | `then` を待つ上限（秒、既定 5） |
| 新規 `config.interrupts` | 割り込みの扱い（`allow`/`report`/`fail`） |
| 新規 `config.on_failure` | `continue`（既定）/`stop` |
| 新規 `config.reset` | 開始前に止める関連パッケージなど（試作の `reset_packages`） |
| 新規 `config.model` | 使うモデル（既定 haiku） |

## 12. 出力

出力先を `.uiai/results/<timestamp>/` に一本化する（現行は `.adb-test/`・`.ios-test/`・`.web-test/` に分かれている）。

```
.uiai/results/<timestamp>/
  summary.md
  events.jsonl       # 失敗などのイベント（リアルタイム通知の元）
  <scenario>/
    result.json      # 呼び出しごとの操作・座標・AI の理由・読み取った文字・判定・時間・トークン
    report.md
    report.html      # 時系列: 画像＋タップ位置の印＋AI の理由＋判定
    call_NN.jpg      # AI に送った画像
```

終了コードは、全シナリオ合格なら 0、それ以外は 1（CI 用）。

## 14. 進め方

| 段階 | 内容 | 完了の目安 |
|---|---|---|
| 1. エンジン化 | 試作を `engine/` に移植。Android（画像）と Web。シナリオ機能（変数・プレースホルダー・replay・wait・strict）、失敗時の続行、イベント出力と Webhook、レポート、CLI（`run`/`check`/`setup`/`watch`） | 既存のサンプルシナリオと計測用シナリオが通る。同じシナリオを 5 回続けて走らせ、判定が毎回一致する。Web シナリオが mac・Linux・Windows で通る |
| 2. プラグイン統合 | `bin/` の起動スクリプト、`/uiai:test` スキル（バックグラウンド実行と失敗のリアルタイム通知）。旧エージェントとコンパイル一式を削除。README・scenario-check を更新 | プラグインとして別の作業フォルダから実行でき、失敗がチャットに届く |
| 3. iOS と日本語入力 | iOS シミュレータのドライバ（Mac のみ）、Android の日本語入力 | iOS で計測用シナリオが通る |
| 4. 速度・コスト・拡張 | セッションの作り直し（画像を溜めない）、複数端末での並列実行、API バックエンド、sonnet での再判定、OS のデスクトップ通知、Windows・Linux からの iOS 操作 | 50 ステップ級のシナリオで、1 ステップの時間が序盤と終盤で変わらない |

## 15. リスクと未検証事項

| 項目 | 内容・対策 |
|---|---|
| 判定の揺れ | 同じ画面でも実行ごとに判定が変わる可能性がある。段階 1 で繰り返し実行して一致率を測る |
| 誤った合格 | AI が楽観的に合格とする可能性がある。証拠画像と読み取った文字をレポートに残す |
| strict の限界 | 見た目で区別できない文字（空白の数・半角と全角の一部）は判定できない。試験では誤りは安全側（不一致と判定）だったが、件数は少ない |
| 画面にない対象 | 座標だけを答えさせる試験では、存在しない対象にも座標を返した。見つからないときはスクロールか `fail` を選ぶようプロンプトで明示し、タップ後に画面が変わらなければ AI に伝える |
| 長いシナリオ | 画像が溜まって会話が伸びる（段階 4 で対策） |
| iOS | idb の速さと安定性は未計測。Windows・Linux からは Mac か実機の準備が必要 |
| Android の日本語入力 | `adb input text` は非対応。ADB Keyboard などの IME かクリップボード経由が必要（未検証） |
| Windows | 文字コード・`claude` の起動・PowerShell からの `bin/` 実行は未検証 |
| 実機 | 計測はエミュレータのみ。USB 接続の実機では撮影速度が変わる可能性がある |
| Claude Code CLI への依存 | stream-json や画像入力の仕様が変わる可能性がある。API バックエンドを逃げ道として用意する |
| 画面内容の送信 | スクリーンショットは Anthropic の API に送られる（現行方式も同じ）。機密情報を含むアプリでの利用は注意事項として明記する |
| コスト | 1 回の入力は画像込みで 1,500〜2,000 トークン程度、1 シナリオで 10〜25 回。料金は未試算 |
| 小さい対象・特殊な画面 | 48dp 未満の対象や Canvas・ゲーム画面は未検証 |
