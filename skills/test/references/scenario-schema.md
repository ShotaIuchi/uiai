# シナリオ仕様

UI テストのシナリオを YAML で書くための仕様。Android・iOS・Web で共通。
エンジンは 1 ステップごとにスクリーンショットを AI に見せ、`do` の操作と `then` の判定を AI に任せる。
UI ツリー・DOM・リソース ID は使わないので、**画面に見えるもの**で書く。

形式の検査は `uiai check <ファイル>`（`/uiai:scenario-check`）で行う。

## 基本構造

```yaml
name: "ログインテスト"
app:
  android: "com.example.app"        # パッケージ名
  ios: "com.example.App"            # Bundle ID（Mac のシミュレータか、USB でつないだ iPhone）
  web: "https://example.com/login"  # 最初に開く URL

variables:
  email: "test@example.com"
  password:
    env: TEST_PASSWORD              # 環境変数から読む
    secret: true                    # AI に値を渡さず、記録からも伏せる

steps:
  - id: "ログイン"
    actions:
      - do: "アプリを起動する"
      - then: "ログイン画面が表示されていること"
      - do: "メールアドレス「(email)」、パスワード「(password)」でログインする"
      - then: "ホーム画面が表示されていること"
      - then: "エラーが表示されていないこと"
```

## 最上位のフィールド

| フィールド | 必須 | 説明 |
|---|---|---|
| `name` | ✅ | シナリオ名 |
| `app` | ✅ | 対象のアプリ・ページ（下記） |
| `variables` | - | 変数（下記） |
| `config` | - | 実行の設定（下記） |
| `steps` | ✅ | セクションのリスト |

## app

プラットフォームごとに書く（推奨）。

```yaml
app:
  android: "com.example.app"     # パッケージ名
  ios: "com.example.App"         # Bundle ID
  web: "https://example.com"     # http(s)・file の URL、またはシナリオからの相対パスの .html
```

文字列でも書ける。`http://`・`https://` で始まるか `.html` で終わるなら Web、それ以外は Android と iOS で同じ識別子という意味になる。

```yaml
app: "com.example.app"           # Android と iOS
app: "https://example.com"       # Web
```

### 実行するプラットフォームの決まり方

1. `uiai run --platform android|ios|web|all` の指定があれば従う。
2. なければ、`app` に書かれたプラットフォームのうち、**いま実行できるもの**（接続中の Android 端末、USB でつないだ iPhone か起動中の iOS シミュレータ。Web は常に可）に絞る。
3. 1 つに決まればそれで実行する。複数残ったら実行せず、`--platform` の指定を求める（`all` なら残った全部で実行する）。

セクションに `on`（下記）があるときは次のようになる。

- `--platform` の指定がなければ、`on` に書いたプラットフォームは候補から外す（`on: web` のセクションがある Android のテストは Android で実行する）。
- すべてのセクションに `on` があれば、最初のセクションのプラットフォームで実行する。
- `on` に書いたプラットフォームも、いま実行できなければならない。できなければそのシナリオは実行しない。

## variables

`do`・`then` の中で `(名前)` と書くと値に置き換わる。変数名は英字か `_` で始まり、英数字と `_` だけ。
文字どおりの括弧は `\(` と `\)` で書く。

```yaml
variables:
  email: "test@example.com"        # 固定値
  office: "東京本社"
  password:                        # 値なし → 実行時に入力
  api_key: null                    # 値なし（明示的）
  token:
    prompt: "トークンを入力"         # 入力を求めるときの文言
  user_id:
    env: TEST_USER_ID              # 環境変数から読む
  login_password:
    env: TEST_PASSWORD
    secret: true                   # 秘密の値
```

値は次の順に決まる。どれもなければ、そのシナリオは実行しない（エラーとして報告する）。

1. `uiai run --var 名前=値`
2. シナリオに書いた値（`""` も有効な値）
3. `env:` の環境変数
4. 対話入力（端末から直接実行したときだけ。CI や `/uiai:test` のバックグラウンド実行では入力できない）

### 秘密の値（`secret: true`）

- 値を AI に渡さない。AI は `(login_password)` という形のまま入力を指示し、エンジンが入力の直前に本当の値に置き換える。
- `result.json`・レポート・イベント・Webhook では値を `****` に伏せる。
- `then` では使えない（AI が照合できないため、`uiai check` がエラー E033 にする）。
- 値は `env:` で渡すのが基本。シナリオファイルに書かない。
- 画面に平文で表示された値（伏せ字でない入力欄など）は、スクリーンショットとして AI に送られる。これは防げない。

## steps（セクション）

| フィールド | 説明 |
|---|---|
| `id` | セクション名（必須・重複不可） |
| `actions` | `do`・`then` のリスト |
| `replay` | 前のセクションの `do` をもう一度実行する（下記） |
| `on` | このセクションを実行するデバイス: `android` / `ios` / `web`（下記）。書かなければ、実行時に決まったデバイス |

`actions` と `replay` の少なくとも一方が要る。セクションの代わりに、別のシナリオを読み込む `include` も書ける（下記）。

### replay

```yaml
steps:
  - id: "ログイン"
    actions:
      - do: "ログインする"
      - then: "ホーム画面が表示されていること"
  - id: "再ログイン"
    replay:
      from: "ログイン"     # この範囲のセクションの `do` だけを実行（`then` は飛ばす）
      to: "ログイン"       # from と同じなら 1 セクションだけ
    actions:
      - then: "ホーム画面が表示されていること"
```

- `from` から `to` までのセクションを順に実行する。対象に `replay` があれば、それも展開する。
- `replay` を先に、そのあと自分の `actions` を実行する。
- `from` は `to` より前のセクションでなければならない。循環はエラー。
- 繰り返す `do` は、`replay` を書いたセクションのデバイスで実行する。`on` が違うセクションを範囲に含むと、`uiai check` が警告する（W011）。

### on（別のデバイスで実行するセクション）

1 つのシナリオの途中で、別のデバイスに切り替えて操作・確認する。たとえば、Android アプリで申請し、Web の管理画面で承認して、Android に戻って結果を確かめる。

```yaml
app:
  android: "com.example.app"
  web: "https://admin.example.com"   # on: web のセクションが開く
steps:
  - id: "申請"
    actions:
      - do: "アプリを開いて休暇を申請する"
      - then: "「申請中」と表示されていること"
  - id: "承認"
    on: web                          # このセクションだけ Web で実行する
    actions:
      - do: "管理画面を開いて、最新の申請を承認する"
      - then: "「承認済み」と表示されていること"
  - id: "結果"                         # on がない: 実行時のデバイス（ここでは Android）に戻る
    actions:
      - do: "申請一覧を開き直す"
      - then: "「承認済み」と表示されていること"
        timeout: 30                  # 反映を待つ
```

- `on` のないセクションは、実行時に決まったデバイス（`--platform`、または自動で選ばれたもの）で実行する。
- `on` に書くプラットフォームの対象（パッケージ名・URL）は `app` に書く（ないと E018）。
- 開始前に、使うすべてのデバイスを初期化する（アプリを止める・まっさらなブラウザにする）。Web のページは、そのデバイスの最初の `do` で開く（「管理画面を開いて…」のように書く）。
- 切り替えの前に、それまでのデバイスに残っている `then` を判定し、最後の `do` の `wait` を待ち終える。切り替えのときにアプリやページを初期化し直すことはない（戻ってきたら、離れたときの画面から続ける）。
- AI との会話はデバイスごとに分かれる。戻ってきたデバイスの会話には、ほかのデバイスで行ったステップを文字で伝える。
- `on_failure: next_section` では、各セクションの前に、そのセクションのデバイスを初期化する。
- `config` はすべてのデバイスに同じように効く（`stop_app_after` は、使ったすべてのデバイスでアプリを止める）。
- レポートには、各ステップを実行したデバイスがセクション名の横に出る（例: `承認 @ web`）。
- `--parallel` では、`on` のあるシナリオは、ほかのシナリオを並列に実行し終えたあとに 1 件ずつ実行する（複数のデバイスを同時に使うため）。
- Web のページが自動で更新されない場合、`then` の `timeout` で待っても画面は変わらない。ページを開き直す `do` を挟む。
- YAML では `on` が真偽値として読まれることがあるが、uiai はセクションのキーの `on` をそのまま読む。

### include（別のシナリオを読み込む）

ログインや管理画面での承認など、いくつものシナリオで使う手順を 1 つのシナリオにしておき、その場に読み込む。

```yaml
# parts/approve.yaml（単体でも実行できるシナリオ）
name: 承認
app:
  web: "https://admin.example.com"
steps:
  - id: 承認する
    actions:
      - do: "管理画面を開いて、最新の申請を承認する"
      - then: "「承認済み」と表示されていること"
```

```yaml
# leave.yaml
name: 休暇申請
app:
  android: "com.example.app"
steps:
  - id: 申請
    actions:
      - do: "アプリを開いて休暇を申請する"
  - include: parts/approve.yaml   # このファイルからの相対パス
    on: web                       # 読み込んだセクションを Web で実行する
  - id: 結果
    actions:
      - do: "申請一覧を開き直す"
      - then: "「承認済み」と表示されていること"
```

- 読み込んだシナリオのセクションが、その位置に順に入る（`then` も判定する）。セクションの `id` は「`include` の `id`（なければ読み込んだシナリオの `name`）/ 元の `id`」になる（例: `承認/承認する`）。同じシナリオを 2 回読み込むときは、`id` を変える。
- `include` に書けるのは `id` と `on` だけ。
- `on` を書くと、読み込んだセクションのうち `on` のないものを、そのデバイスで実行する（自分の `on` があるセクションはそのまま）。書かなければ、`on` のないセクションは実行時のデバイスで実行する。
- 読み込んだセクションは、読み込んだシナリオの `app` の対象（パッケージ名・URL）で動く。読み込む側の `app` にないプラットフォームは、読み込む側にも足す（上の例では Web）。実行するプラットフォームは、読み込む側のファイル自身の `app` から決まる（読み込みで足したプラットフォームは候補にしない）。
- 変数は両方のものを使える。同じ名前があれば読み込む側の定義を使う（値を差し替えられる）。どちらかで `secret: true` なら秘密の値として扱う。
- 読み込んだシナリオの `config` は使わない。読み込む側の `config` が全体に効く。
- 読み込むシナリオは、単体でもエラーのないシナリオでなければならない（エラーがあれば E042）。読み込んだシナリオがさらに `include` してもよい。循環はエラー（E041）。
- 開始前に、読み込んだシナリオの対象も含めて、使うアプリをすべて初期化する。
- フォルダを指定して実行すると、読み込まれる側のファイルも 1 つのシナリオとして実行される。

## actions（`do` と `then`）

| フィールド | 対象 | 説明 |
|---|---|---|
| `do` | - | やること（自然言語） |
| `then` | - | 期待する画面の状態（自然言語） |
| `wait` | 両方 | 直前の画面操作が終わってから、次の画面を撮るまでの最短の時間（秒）。`do` は次の撮影、`then` は判定に使う撮影が対象（下記） |
| `strict` | 両方 | 一字一句の完全一致で判定する（下記） |
| `optional` | `do` | 失敗しても打ち切らず、「スキップ」として次へ進む（データの登録など、すでに済んでいてもよい準備のステップ用。下記） |
| `timeout` | `then` | 合格になるまで待つ上限（秒、既定 `config.then_timeout` = 5） |
| `observe` | `then` | 「〜がないこと」を見張り続ける時間（秒、既定 2） |

1 行に `do` と `then` を両方書くことはできない。

### wait の数え方

`wait` は、操作のあとに上乗せする待ち時間ではない。直前の画面操作（タップ・入力・キー・戻る・スクロール・アプリの起動）が終わった時刻から数え、その秒数がたつまで次の画面を撮らない。

- 画面が落ち着くのを待つ処理は、その間に並行して進む。先に落ち着いたら、時間がたった時点でもう一度撮り、変わっていなければその画像を使う。変わっていれば、落ち着くのを待ち直す。
- `do` と `then` の両方に付けても足し算にはならず、長い方になる。
- 直前の操作から、すでにその秒数がたっていれば待たない（例: `do` が何も操作せずに終わったとき）。シナリオやセクションの初期化のあと、まだ操作していなければ、`wait` に来た時点から数える。
- 次の撮影の前に、セクションの初期化（`on_failure: next_section`）やシナリオの終わりが来るときは、そこで残りの時間を待つ（保存の途中でアプリを止めないため）。

### do の動き

- AI は画面を見て、`do` を達成する操作（タップ・入力・キー・戻る・スクロール・アプリの起動）を選ぶ。1 つの `do` に複数の操作が要るときは続けて行う（上限 `config.max_actions`、既定 5 回）。
- 達成できない（対象が見つからない、上限を超えた、エラーのダイアログが出た）と、その `do` は失敗になり、既定ではシナリオの残りを「未実行」にして打ち切る（`config.on_failure`）。
- 想定外のダイアログ（Cookie の同意、通知の許可など）は閉じて続ける。扱いは `config.interrupts` で決める。エラーを知らせるダイアログは閉じずに失敗にする。

### then の動き

- 直前の `do` が終わって画面が落ち着いたところで判定する。不合格なら `timeout` まで約 1 秒おきに判定し直す（読み込み待ちに強い）。
- `timeout` を過ぎても不合格のときは、確定する前に別のモデル（既定 sonnet）が同じ画像で判定し直す。そのモデルが合格とすれば合格にし、判定が分かれたことを警告に残す（画面があいまいな可能性があるため）。不合格なら、両方の理由を残して不合格にする。モデルは `uiai run --rejudge-model` で変えられる（`none` で判定し直さない）。
- 判定のために、AI は画面の外を確かめるスクロールをすることがある。
- 「エラーが表示されていないこと」のような**否定形**は、合格してからも `observe` 秒だけ画面を見張り、変化があれば判定し直す。遅れて出るエラーを捉えるため。それより遅く出るものを捉えたいときは `observe` を延ばす。
- `then` が不合格でも実行は続ける。

### strict（厳格モード）

`strict: true`（または `config.strict: true` で全体の既定にする）の行は、AI が画面の文字を一字一句読み取り、完全に一致するときだけ合格にする。読み取った文字はレポートに残る。

- 末尾が「…」で省略されている、伏せ字、画面からはみ出しているなど、全体が読めないときは推測せず不合格にする。
- 見た目で区別できない文字（半角と全角の空白、半角「¥」と全角「￥」、空白の数など）は判定できない。
- 個別の指定が `config.strict` より優先される。

## config

```yaml
config:
  timeout: 600              # シナリオ全体の上限（秒、既定 600）
  then_timeout: 5           # then を待つ上限の既定（秒）
  max_actions: 5            # 1 つの do に使える操作の回数
  strict: false             # 全行を厳格モードにする
  clear_data_before: false  # 開始前にアプリのデータを消す（Android: pm clear。Web は毎回まっさらなブラウザで始まる）
  stop_app_after: false     # 終了後にアプリを止める
  reset: []                 # 開始前に止める関連パッケージ（Android）
  on_failure: stop_scenario # do が失敗したとき: stop_scenario / next_section / stop_all
  interrupts:
    mode: report            # 想定外のダイアログ: allow / report / fail
    allow: ["Cookie の同意"] # 黙って閉じてよいダイアログ
  model: haiku              # 使うモデル（--model が優先）
  type_delay: 0             # 文字入力の 1 文字ごとの間隔（ミリ秒、既定 0 = 最速。--type-delay が優先）
```

| キー | 説明 |
|---|---|
| `timeout` | AI 方式は 1 ステップ 3〜6 秒かかる。「`do` の数 × 10 秒」より短いと `uiai check` が警告する |
| `on_failure` | `stop_scenario`（既定）: 残りを未実行にして次のシナリオへ。`next_section`: 次のセクションへ進む（各セクションの前にアプリを初期化する。`on` のあるセクションでは、そのデバイスを初期化する。セクションが互いに独立しているとき用）。`stop_all`: 実行全体を止める |
| `type_delay` | 1 文字ずつ打つときの、キーとキーの間隔の最小値（ミリ秒）。最初のキーも、直前の操作（入力欄のタップなど）から同じだけ空ける。速い入力で文字が落ちるアプリや、入力ごとに反応する画面を試すとき用。1 キーを送るのに時間がかかる環境では、指定より間が空く（Android は 1 キー約 0.2 秒）。Android: ASCII を 1 キーずつ送る。日本語など ASCII 以外は、間隔に関係なく一度に貼り付ける。iPhone: WebDriverAgent に 1 秒あたりの文字数（整数）で渡す（例: 100 → 10 文字/秒、300 → 3 文字/秒。1 秒を超えると 1 文字ずつ送る）。iOS シミュレータ: AXe を 1 文字ずつ呼ぶ。Web: Playwright の `delay` |
| `interrupts.mode` | `report`（既定）: 閉じて続け、警告にする。`allow`: 閉じて続け、記録だけ残す。`fail`: 閉じずに `do` を失敗にする。`allow` のリストに当たるダイアログはどのモードでも警告にしない |

### optional（失敗してもよい do）

```yaml
- do: "名前に「taro」を入力して「登録する」を押す"
  optional: true            # すでに登録済みでもよい
- do: "「一覧」タブを開く"
- then: "一覧に taro がある"  # 必要な状態は then で確かめる
```

- `optional: true` の `do` は、最後の操作のあとに結果の画面を AI がもう一度見てから完了になる。その操作で「すでに登録されています」などのメッセージやダイアログが出たら、AI がそれを閉じてから失敗を返す。
- 失敗した `optional` の `do` は「スキップ（optional）」として記録し、シナリオは次のステップへ進む。警告にはしない（ほかに問題がなければシナリオは合格）。スキップしたステップは、まとめ（`summary.md`）とレポートに理由つきで出る。
- 本当の不具合で失敗しても、同じくスキップになる。先へ進むのに必要な状態（例: 一覧に taro がある）は `then` で確かめる。
- `config.timeout`（シナリオ全体の上限）を超えたときは、`optional` でも打ち切る。
- その `do` を始める前から出ていたエラーのダイアログは、その `do` のものとは扱われない。エラー表示として失敗し（スキップになる）、ダイアログは残る。

## 結果

シナリオは「合格」「警告付き合格」「不合格」、各ステップは「合格」「不合格」「未実行」「スキップ（optional）」になる。
次のことは警告として記録する（合否は変えない）。

- 想定外のダイアログを閉じた（`interrupts`）
- 最初の `do` 以外で、文に起動の指示がないのにアプリを起動した
- 何もしなかった（すでに満たされていた。前提がシナリオの想定と違う可能性）
- 文が戻ることを指示していないのに「戻る」を挟んだ（遠回りの可能性）
- `then` の判定が分かれた（最初の判定は不合格、判定し直したモデルは合格で、合格にした）

## 書き方のこつ

**do**: 1 つの `do` は利用者から見た 1 つの目的にする。画面に見える文字で対象を書く。

```yaml
- do: "「ログイン」ボタンをタップする"
- do: "検索欄に「東京」と入力して検索する"
- do: "一覧を下にスクロールして「プライバシー」を開く"
- do: "戻る"
- do: "アプリを再起動する"
```

**then**: 画面を見て判断できる状態を書く。文字を厳密に確かめたいときだけ `strict` を使う。

```yaml
- then: "ホーム画面が表示されていること"
- then: "「東京本社」と表示されていること"
  strict: true
- then: "エラーが表示されていないこと"
- then: "保存完了のメッセージが表示されること"
  timeout: 10                # 時間がかかる処理
```

避けること:

- リソース ID・クラス名・XPath など、画面に見えないものでの指定
- 1 つの `do` に、別々の目的を詰め込むこと（失敗したときに原因が分からなくなる）
- 色の微妙な違いなど、画像で判断しにくい状態だけに頼る `then`

## 制限

- iOS は Mac のシミュレータと、Mac に USB でつないだ iPhone。シミュレータは起動しておき、操作には [AXe](https://github.com/cameroncooke/AXe) が要る。iPhone は [WebDriverAgent](https://github.com/appium/WebDriverAgent) で操作する。初回の実行時に取得し、Xcode にサインインしたチームで署名してビルドする（数分かかる）。iPhone とシミュレータの両方があるときは `--udid` で選ぶ。
- iPhone を使う前に、iPhone 側で「デベロッパモード」（設定 > プライバシーとセキュリティ）と、設定 > デベロッパの「UI オートメーションを有効にする」をオンにする。無料の Apple ID のチームでは、初回に設定 > 一般 > VPN とデバイス管理で開発元を信頼する必要があり、署名は 7 日で切れる（切れていれば、実行のたびに行うビルドの確認で作り直される）。
- AI が使える操作は、タップ・文字入力・キー・戻る・スクロール・アプリの起動だけ。長押し・ドラッグ・ピンチは使えない。
- iOS シミュレータは日本語などの ASCII 以外の文字を入力できない（その `do` は失敗する）。iPhone は WebDriverAgent の文字入力を使う（ASCII 以外が入るかは未検証）。
- Android の文字は、端末のクリップボードに入れて貼り付ける（`config.type_delay` を指定したときの ASCII は 1 キーずつ打つ）。クリップボードの中身は上書きされる。貼り付けの直後は、クリップボードの表示や、キーボードの候補欄に貼り付けた文字列が出ることがある。秘密の値（`secret: true`）を含む ASCII の入力は、クリップボードを通さずに打つ（ASCII 以外の秘密の値は貼り付ける）。
- iOS の「戻る」は画面の左端からのスワイプ。戻るボタンがある画面では AI がボタンを押す。
- iOS では `config.clear_data_before` は効かない（アプリのデータは消さない）。iPhone でも同じ。
- Android の `FLAG_SECURE` の画面は撮影すると真っ黒になる可能性が高く、判定できない。
- スクリーンショットは Anthropic の API に送られる。機密情報を表示するアプリでは注意する。

## 旧形式からの変更

旧形式のシナリオはそのまま読める。意味が変わったものと、廃止したものは次のとおり。

| 項目 | 変更 |
|---|---|
| `strict` | UI ツリーのテキスト照合から、AI による画像での一字一句の照合に変わった |
| `verify`・`config.verify` | 廃止。書かれていても警告（W007）を出して無視する |
| `app`（文字列） | URL・`.html` なら Web として扱うようになった |
| `app.web` | 最初に開く URL。`.html` への相対パスも書ける |
| `config.timeout` | 意味は同じ。既定は 600 秒 |
| 追加 | `variables` の `env`・`secret`、セクションの `on`、`steps` の `include`、`do` の `optional`、`then` の `timeout`・`observe`、`config` の `then_timeout`・`max_actions`・`interrupts`・`on_failure`・`reset`・`model`・`type_delay` |
