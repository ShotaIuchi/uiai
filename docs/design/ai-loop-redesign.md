# uiai 再設計案: AI を毎ステップ挟む実行方式（コンパイル廃止）

- ステータス: 段階 1〜3 実装済み（14.1〜14.3。CI 上での動作は未検証）。段階 4 は一部実装（14.4。API バックエンドは偽の応答でのテストまでで、実際の API では未検証。Windows・Linux からの iOS 操作は未着手）
- 作成日: 2026-11-12（同日、設計レビューの指摘を反映）
- 根拠となる試作: `prototype/ai-loop/`（コミット `225da4f`。段階 1 で `engine/` へ移植して削除）

## 1. 結論

**プログラムがループを回し、AI には 1 ステップにつき 1 回だけ判断させる。画面の入力はスクリーンショットだけにする。コンパイル（決定的リプレイ）は廃止する。**

- AI の判断は 1 回あたり約 1 秒で、ボトルネックではない。
- 画像だけで、タップ位置・状態の判定・割り込み処理・一字一句の文字確認まで実用的にこなせた。
- 画面取得は、スクリーンショットなら Android 約 0.15 秒、Web 約 0.02 秒で、UI ツリー（`uiautomator dump` は 2〜30 秒、画面によっては取得できない）より速く安定している。
- プラットフォームごとの差は「撮る・押す・打つ」などの小さな部品だけに閉じ込められる。Web 版は、この部品を差し替えるだけで動いた。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 既定のモデル | haiku |
| スキルの形 | `/uiai:test` 1 つに統合（`platform` 引数。省略時は 11.1 の規則で決める） |
| 配布と依存 | プラグインの `bin/` に起動スクリプトを置き、エンジンの依存は uv で自動導入する（版は固定） |
| strict（厳密な判定） | AI による画像判定（一字一句の完全一致）。AI が読み取った文字をレポートに残す。全体が読めないときは推測せず不合格 |
| 失敗したとき | 全シナリオを最後まで走らせる。`then` の不合格は記録して続行。`do` が実行できなければそのシナリオを打ち切り（残りは「未実行」）、次のシナリオへ。失敗はリアルタイムに通知する |
| AI の裁量 | 割り込みの片付け・アプリの再起動・「何もしない」・遠回りは許すが、警告として記録する。エラーを知らせるダイアログは片付けない |
| 秘密の値 | AI に値を渡さない。記録・通知からも伏せる |
| iOS | Mac とシミュレータに限定する。Windows・Linux からの iOS 操作は後から足せる作りにする |

## 3. 現行方式の問題

| 問題 | 内容 |
|---|---|
| 遅い | ランナー（サブエージェント）がシナリオ全体を回し、評価エージェントがあとから `then` を判定する。画面取得の `uiautomator dump` は 1 回 2〜3 秒かかり、30 秒止まることや失敗することもある |
| 不確定要素に弱い | コンパイル結果は「前回と同じ画面が出る」前提で動く。トースト・予期しないダイアログ・読み込み時間の揺れに弱い |
| 対応の偏り | コンパイルは Android のみ。iOS/Web は未対応 |
| 抜け | `ai_required` と判定された `do` は実行されない |

## 4. 計測結果（根拠）

いずれも Claude Code（`claude -p` の持続セッション、stream-json）経由で計測した。各条件の実行は 1〜3 回で、統計的な裏付けとしては少ない。

### 4.1 通しの実行

| 対象 | 画面の取り方 | モデル | 合計 | 1 ステップ | AI 1 回 | 判定 |
|---|---|---|---|---|---|---|
| Android 設定アプリ（`do` 9） | UI ツリー（`adb` dump） | sonnet | 111.8 秒 | 12.4 秒 | 1.83 秒 | 5/6 |
| 同上 | UI ツリー（uiautomator2） | sonnet | 49.5 秒 | 5.5 秒 | 2.02 秒 | 6/6 |
| 同上 | **画像のみ** | sonnet ×3 | 46.0〜50.0 秒 | 5.1〜5.6 秒 | 1.09〜1.22 秒 | 6/6 ×3 |
| 同上 | **画像のみ** | haiku ×2 | 47.6〜51.2 秒 | 5.3〜5.7 秒 | 1.21〜1.27 秒 | 6/6 ×2 |
| Web 試験アプリ（`do` 11） | **画像のみ** | sonnet ×2 | 27.8〜30.9 秒 | 2.5〜2.8 秒 | 0.96〜1.04 秒 | 8/8 ×2 |
| 同上 | **画像のみ** | haiku ×2 | 33.0〜34.1 秒 | 3.0〜3.1 秒 | 0.93〜0.94 秒 | 8/8 ×2 |
| Wikipedia（実サイト、`do` 3） | **画像のみ** | sonnet/haiku ×2 ずつ | 14.0〜17.3 秒 | 4.7〜5.8 秒 | 0.98〜1.16 秒 | 3/3 ×4 |

- Android の画像方式の時間は、約半分がアプリ自身のアニメーションや読み込みの待ち（撮影自体は 0.15 秒）、約 4 割が AI。
- Web は撮影が速いため、約 7 割が AI。
- 判定の正しさは、AI に送った画像と突き合わせて確認した。確認したのは抜き取りで、画像のみ方式の Android（sonnet・haiku 各 1 本）、Web 試験アプリ（haiku 1 本）、Wikipedia（haiku 1 本）。UI ツリー方式の 6/6 は画像では確認していない。

### 4.2 Web 試験アプリで確かめた不確定要素

| 要素 | 結果 |
|---|---|
| 3 秒で消えるトースト | 操作直後の静止画面で捉えて判定できた |
| シナリオに書いていない Cookie 同意ダイアログ | AI が割り込みとして閉じて続行した |
| 保存前の確認ダイアログ | 取り直しの中で「保存する」を押し、判定し直した |
| 2 秒かかる検索（読み込み表示あり） | 取り直しで待ってから合格した |
| 日本語入力 | Web は問題なし。Android の `adb input text` は日本語非対応（未対応） |

### 4.3 画像だけでのタップ精度（Android、座標だけを答えさせる試験）

| 画面 | sonnet | haiku |
|---|---|---|
| 設定アプリの各項目・スイッチ・戻る矢印 | 7/7 | 7/7 |
| 言語一覧の末尾（日本語・简体中文・繁體中文・粵語・한국어） | 5/5 | 5/5 |
| ホーム画面の小アイコン（126px 角） | 5/5 | 5/5 |
| クイック設定の小アイコン（126px 角） | 5/5 | 5/5 |
| キーボード（入力欄が「kem」になるかで判定） | 5/5 | 5/5 |

1 回の応答は sonnet 約 0.9〜1.2 秒、haiku 約 0.7 秒。試した中で一番小さい対象は 126px 角（48dp 相当）。

### 4.4 画像だけでの厳密な文字判定（strict の根拠）

| 試験 | haiku | sonnet |
|---|---|---|
| Web: 紛らわしい表記の判定（正しい表記 8 問・紛らわしい別表記 8 問） | 14/16 | 14/16 |
| └ 紛らわしい別表記を「不一致」と見抜けたか | 8/8 | 8/8 |
| └ 正しい表記を「一致」と認めたか | 6/8 | 6/8 |
| Android 端末情報画面の 5 項目（15 桁の IMEI を含む）の書き起こし（540×1200 / 1080×2400） | 5/5 / 5/5 | 5/5 / 5/5 |

- 見分けられた: 「本社」と「本店」、英字 O と数字 0、小文字 l と数字 1 と大文字 I、長音記号「ー」とハイフン、全角英字、11px の小さい文字。
- 間違えた 2 問は、画面上の見た目ではほぼ区別できない文字だった（半角「¥」を全角「￥」と読んだ、半角スペース 2 つを全角スペース 1 つと読んだ）。どちらも「一致しているのに不一致」とした安全側の誤りで、紛らわしい別表記を誤って合格にしたことはない。
- 同じ試験中、Android の端末情報画面では `uiautomator dump` が「could not get idle state」で毎回失敗した。UI ツリーで照合する方式は、画面によってはそもそも動かない。

| 処理 | 時間 |

| Android uiautomator2（常駐） | 0.04 秒。ただし操作直後は古い画面を返す。`adb` の dump と同時に使えない |
| Android スクリーンショット（raw） | 0.15 秒 |
| Web スクリーンショット | 0.02 秒 |
| AI 1 回（画像あり・返答 約 75 トークン） | 0.9〜1.3 秒 |
| AI 1 回（UI ツリー文字列） | 約 2.0 秒（画像より遅い理由は未確認） |

## 5. 設計方針

1. **プログラムがループを回し、AI は判断だけ**: `do` 1 つにつき AI を 1 回呼ぶ。その 1 回で「前の `then` の判定」と「次の操作」を同時に返させる。
2. **画面の入力はスクリーンショットだけ**: UI ツリーは使わない（取得が遅く、画面によっては取れないため）。
3. **`then` は「落ち着いた画面で満たされるか」で判定**: 不合格ならすぐ失敗にせず、上限時間まで待って取り直す。割り込みを片付ける操作も挟める。
4. **プラットフォーム差は小さな部品（ドライバ）に閉じ込める**: ループ・AI・レポート・通知は全プラットフォーム共通。
5. **決定的リプレイ（コンパイル）は持たない**: 毎回 AI が画面を見て判断する。
6. **すべての判断を証拠付きで残す**: 各呼び出しの画像・操作位置・AI の理由・読み取った文字をレポートに残し、あとから人が確かめられるようにする。
7. **全シナリオを最後まで走らせ、失敗はその場で知らせる**。ただし前提が崩れたシナリオは打ち切る（壊れた画面のまま操作を続けても意味のある結果にならないため）。
8. **AI の裁量は狭くし、逸脱は必ず記録する**: AI が「うまくやってしまう」ことで不具合が隠れるのを防ぐ。
9. **秘密の値は AI に渡さない**。

## 6. プラグイン構成と動作環境

### 6.1 構成

```
uiai/
├── .claude-plugin/plugin.json
├── bin/
│   ├── uiai              # mac・Linux・Windows（Git Bash）用の起動スクリプト
│   └── uiai.cmd          # Windows（PowerShell）用
├── engine/
│   ├── main.py           # 依存ライブラリを版を固定してファイル先頭に宣言（PEP 723）。uv run --script で起動
│   └── uiai/
│       ├── cli.py        # uiai run / check / setup / watch
│       ├── scenario.py   # YAML 読込・変数（秘密の値を含む）・プレースホルダー・replay 展開・検査
│       ├── platform.py   # 実行するプラットフォームの決定（11.1）
│       ├── loop.py       # ステップ実行・then 判定・取り直し・割り込み・逸脱の記録・失敗時の打ち切り
│       ├── settle.py     # 画面の「変化待ち → 静止待ち」
│       ├── ai/protocol.py      # AI への指示と応答の読み取り
│       ├── ai/claude_code.py   # 既定: claude -p の持続セッション
│       ├── ai/api.py           # 任意: ANTHROPIC_API_KEY で直接呼ぶ（段階 4。実際の API では未検証）
│       ├── drivers/{base,android,ios,web}.py   # ios は段階 3
│       ├── events.py     # 失敗などのイベント出力（stdout と events.jsonl）
│       ├── notify.py     # Webhook など
│       ├── desktop.py    # OS のデスクトップ通知（段階 4）
│       ├── redact.py     # 記録・通知から秘密の値を伏せる
│       └── report.py
│   └── tests/            # 単体テスト（偽の AI・偽のドライバでループの制御を確かめる）
├── examples/             # 走らせられるサンプルと、わざと壊した受け入れ確認用シナリオ（acceptance/）
├── skills/test/
│   ├── SKILL.md                         # /uiai:test
│   └── references/scenario-schema.md    # シナリオ仕様（3 つに分かれていたものを 1 つに）
├── skills/scenario-check/ ほか（13 章）
└── docs/ci/              # CI での使い方（6.4）と GitHub Actions の例
```

- `bin/` に置いたファイルは、プラグインが有効な間、Claude が実行するシェルの PATH に入る（公式仕様。段階 2 で、別の作業フォルダから `claude --plugin-dir` で読み込んで確認済み）。スキルからは `uiai run ...` とだけ書けばよい。`bin/uiai` は改行が LF のままになるよう `.gitattributes` で固定する（Windows で CRLF になると bash で動かない）。
- 前提は uv だけ。uv は mac・Linux・Windows で動き、Python 本体と依存ライブラリ（画像処理・YAML・Playwright など）を自動で用意する。Playwright 用のブラウザは初回に `uiai setup` で取得する。
- **依存は版を固定する**（`==` で指定）。Playwright 本体と、`uiai setup` で取得したブラウザの版がずれると動かないため。uv のロックファイル（`uv lock --script`）の併用は段階 1 で検討する。
- プラグイン用の保存場所 `${CLAUDE_PLUGIN_DATA}` は、スキルから実行するコマンドには渡されない（公式仕様）。依存の管理は uv のキャッシュに任せる。
- Node.js は前提にしない（Claude Code のネイティブ版は Node.js なしで動くため）。

### 6.2 OS ごとの対応

| | mac | Linux | Windows |
|---|---|---|---|
| Android（adb） | ○ | ○ | ○ |
| Web（Playwright） | ○ | ○ | ○ |
| iOS シミュレータ（Xcode と AXe） | ○ | × | × |

Windows での実装上の注意:

- 日本語版 Windows は文字コードの既定が UTF-8 ではない。Claude Code とのやり取り・ファイル入出力は UTF-8 を明示する（試作のままでは日本語が化ける）。
- `claude` の実体は `.exe` か `.cmd` かでばらつくため、実行ファイルの探し方を分けて扱う。
- Claude Code は、Git Bash がなければ PowerShell でコマンドを実行する。`bin/uiai.cmd` が PowerShell から PATH 経由で呼べるかは未検証。

### 6.3 iOS を Windows・Linux から動かす道（後から足す）

iOS シミュレータは Xcode の一部で、macOS でしか動かない。Windows・Linux から動かす道はあるが、どれも Apple 側の何かが要る。

| 方法 | 必要なもの | 評価 |
|---|---|---|
| ① 別の Mac を遠隔操作 | Mac と Xcode がどこかに 1 台。Windows・Linux 側からは、Mac 上の `simctl` と AXe を SSH などで呼ぶ（idb なら、操作側ソフトと Mac 側の常駐ソフトがネットワーク越しに通信する作りがある） | 一番現実的 |
| ② 実機の iPhone を USB で直接つなぐ | 撮影は pymobiledevice3 や go-ios で可能。タップと文字入力には、iPhone 上の WebDriverAgent が必要（Apple の開発者署名付きで、最初の 1 回は Mac の Xcode でビルド） | iOS 17 以降は「実験的」扱いで、手順が重く不安定（未検証） |
| ③ クラウドの実機サービス | Mac 不要。有料 | 予算があれば一番手軽 |

iOS ドライバは、撮影・タップ・入力の担当部分（`simctl` と AXe をローカルで使う／遠隔の Mac で使う／WebDriverAgent の HTTP を使う）を差し替えられる作りにする。

### 6.4 CI で使う

- `bin/uiai` の PATH が通るのは Claude Code の中だけ。CI では、このリポジトリをコミットの SHA で版を固定して取得し、`<取得先>/bin/uiai run ...` をパスで直接呼ぶ。前提は手元と同じく uv だけ。
- AI の呼び出しには Claude Code CLI と、その認証が必要。手元ではユーザーのログインで動くが、CI では API キー（`ANTHROPIC_API_KEY`）か、Claude Code の長期トークン（`claude setup-token` で発行して `CLAUDE_CODE_OAUTH_TOKEN` に設定）を渡す（CI での動作は未検証）。API キーを使える環境なら、段階 4 の API バックエンド（`--backend api`。Claude Code CLI が要らない）の方が向いている（実際の API では未検証）。
- 失敗の通知は Webhook（9 章）、合否は終了コード（12 章）で受け取る。`.uiai/results/` は CI の成果物として保存する。
- Web は headless のブラウザ、Android は CI 上のエミュレータで動かす。
- 手順書と GitHub Actions の例は `docs/ci/`（段階 2 で作成。CI 上では未検証）。

## 7. ドライバ（プラットフォーム部品）

AI が返す座標は「送った画像上の座標」。ドライバが実機の座標に換算する。

| 操作 | Android | iOS シミュレータ | Web |
|---|---|---|---|
| 撮影 | `adb exec-out screencap`（raw） | `xcrun simctl io <UDID> screenshot --type=png -`（標準出力に PNG。約 0.4 秒） | `page.screenshot()` |
| タップ | `input tap` | `axe tap --tap-style physical`（座標はポイント。画像の座標から換算） | `mouse.click` |
| 文字入力 | ASCII は `input text`。それ以外は uiautomator2 でクリップボードに入れて貼り付ける | 英数キー（LANG2）を送ってから `axe type`。ASCII のみ | `keyboard.type` |
| キー | `input keyevent` | `axe key`（HID のキーコード）。ホームは `axe button home` | `keyboard.press` |
| スクロール | `input swipe` | `axe swipe` | `mouse.wheel` |
| 戻る | `keyevent 4` | `axe gesture swipe-from-left-edge`（左端からのスワイプ） | `go_back` |
| 起動 | `monkey -p` | `simctl launch` | `goto` |
| 初期化 | `force-stop`（＋関連パッケージ、任意で `pm clear`） | `simctl terminate`（＋関連アプリ）とホームボタン。データの消去は未対応 | 新しいブラウザコンテキスト |

iOS の操作に idb ではなく [AXe](https://github.com/cameroncooke/AXe) を使う（段階 3 で変更）。AXe は Homebrew で入るコマンド 1 つで済む。idb は Mac 側の常駐ソフト（`idb_companion`）と Python の操作側ソフト（`fb-idb`）の 2 つが要る。

文字入力の制約と、その対処:

- **iOS**: AXe の文字入力はハードウェアキーボードのキーを送るため、US 配列の ASCII しか打てない。シミュレータのキーボードが日本語のローマ字入力だと、ASCII がかなに変わる。そこで、打つ前に英数キー（LANG2）を送る（英語のキーボードでは無視される）。ASCII 以外の文字は、`simctl pbcopy` と Cmd+V での貼り付けを試したが入らなかったため、未対応とした（`do` はエラーで失敗する）。
- **Android**: `adb input text` は ASCII 以外を打てず、シェルからクリップボードに書き込む手段もない。uiautomator2 の `send_keys` を使う。uiautomator2 は端末に補助プログラム（`/data/local/tmp/u2.jar`）を送り込んで `app_process` で動かし、クリップボードへ書き込んでから入力欄に貼り付ける。うまくいかないときは、uiautomator2 が自前の入力メソッド（APK）を入れて打つ。副作用として、端末のクリップボードが上書きされ、Android の版によってはクリップボードの読み書きを知らせる表示が出る。最初の接続に約 3.4 秒かかる。

**撮影できない画面**: Android の保護された画面（`FLAG_SECURE`。決済・パスワード入力の画面など）は、スクリーンショットが真っ黒になる可能性が高い（未検証）。UI ツリーを使わないため代わりの手段はない。真っ黒な画面が `then.timeout` を超えて続いたら、AI に推測させず「撮影できない画面の可能性」という理由で失敗にする。制約としてドキュメントにも明記する。

## 8. 実行ループ

### 8.1 流れ

```
for each scenario:
  for each section:
    if on_failure == next_section and 2 つ目以降のセクション:
        判定待ちの then があれば、判定だけの呼び出しで判定する   # 初期化で画面が変わる前に
        reset(app)
    for each action in section:
      then → pending に積む
      do   → result = run_do(do)
             if result が失敗:
                 残りのステップを「未実行」として記録
                 on_failure に従う（次のシナリオへ／次のセクションへ／全体を止める）
  判定待ちの then があれば、判定だけの呼び出しで判定する       # シナリオ最後の then

run_do(do):
  actions = 0
  while actions < max_actions:                  # 既定 5
    screen = settle(driver)                     # 変化待ち（最大 2 秒）→ 0.1 秒間隔で 2 回連続ほぼ同じ
    reply  = ai.ask(do, pending, screen)        # 前の then の判定と次の操作を 1 回で返す
    if pending:
      if 不合格の then がある and then.timeout 以内:          # 既定 5 秒
          if reply.action が判定のための操作:                 # 前の do を終わらせる操作・画面外を確かめるスクロール
              driver.act(reply.action)
          else:
              sleep(1)
          continue                              # 判定を確定させずに撮り直す
      if 合格した否定形の then がある and まだ観察していない:
          観察時間（既定 2 秒）撮り続け、画面が変わったら continue
      判定を確定（不合格は失敗イベント）し、pending を空にする
    if reply.action が fail: return 失敗
    driver.act(reply.action); actions += 1
    if reply.done: return 成功
  return 失敗                                    # 操作回数の上限
```

判定だけの呼び出しも、取り直し・観察は同じ規則で行う。

### 8.2 `then` の判定

- **タイミング**: 直前の `do` の操作が終わり、画面が落ち着いた最初の画像で判定する。トーストはここで捉える。判定は次の AI 呼び出し（次の `do` の最初の呼び出し）に相乗りさせる。次の `do` がない（シナリオの終わり）か、次の呼び出しの前に初期化が入る場合だけ、判定だけの呼び出しを行う。
- **セッションを作り直しても相乗りは成り立つ**（10 章）: 判定に要るのは現在の画像と `then` の文だけ。前のセクション末尾の `then` は、新しいセッションの最初の呼び出しで判定する。
- **待つ上限は時間で一本化する**: `then.timeout`（秒、既定 5。シナリオ全体の既定は `config.then_timeout`）。不合格なら、上限に達するまで約 1 秒おきに撮り直して判定し直す。
- **判定のための操作**: 取り直しの中で AI ができる操作は、次の 2 つだけ。どちらもレポートに記録する。
  - 前の `do` を終わらせる操作（例: 確認ダイアログの「保存する」）。
  - 画面の外を確かめるスクロール（長い一覧の下の方など）。スクロール位置は戻さない（次の `do` は、AI が現在の画面から判断するため）。
- **否定形の `then`**（「エラーが表示されないこと」など）: AI に、各 `then` が「無いこと」を確かめるものかどうかも答えさせる。合格しても、観察時間（秒、既定 2、`then.observe`）は画面を撮り続け、画面が変わったときだけ判定し直す。画面が変わらなければ AI は呼ばない（かかるのは時間だけ）。
  - 観察は、画面が確定してから行う。ほかの `then` が取り直し中のときや、前の `do` を仕上げる操作（確認ダイアログの「保存する」など）が残っているときは、合格でも確定させずに次の判定へ回す（段階 1 で判明。確認ダイアログが開いたまま観察を終え、保存後に出たエラーを見逃した）。
  - AI には、`then` が合格していても前の `do` が終わっていなければ仕上げの操作を返させる。
- **strict**: 一字一句の完全一致で判定し、読み取った文字を記録する。末尾が「…」で省略されている、伏せ字になっている、画面の外にはみ出しているなど、全体が読めない場合は推測せず「判定できない」として不合格にする。見た目で区別できない文字（半角と全角の空白、半角「¥」と全角「￥」など）は判定できないことを、ドキュメントに明記する。

### 8.3 AI に許す操作と、記録する逸脱

AI が「うまくやってしまう」と不具合が隠れる。許す操作を絞り、逸脱はすべて記録する。

| 逸脱 | 扱い |
|---|---|
| シナリオにないダイアログを閉じた（割り込み） | `config.interrupts` に従う（下記） |
| エラーを知らせるダイアログが出た | 片付けない。シナリオの `do`・`then` がそのダイアログを扱っていなければ、その `do` を失敗にする |
| アプリの起動（`launch`） | 使えるのは、シナリオ最初の `do` と、文がアプリの起動・再起動を指示している `do` だけ（AI への規則）。それ以外で使ったら警告 |
| 何もしなかった（`none`。すでに満たされている） | 許すが警告（前提がシナリオの想定と違う可能性がある） |
| 戻る操作を挟んだ `do`（文が戻ることを指示していない） | 警告（違う画面に入って戻ってきた＝遠回りの可能性がある） |

操作の回数は警告に使わない。当初は「3 回以上かかった `do`」を警告にする案だったが、段階 1 の実画面では「検索画面で「東京」を検索する」（画面を開く・入力・検索）や「…でログインする」（入力・タップ・入力・タップ）のような正常な `do` が 3〜4 回かかり、誤検知しか出なかった。回数はレポートのメモと呼び出し一覧に残す。

割り込みの扱い（`config.interrupts`）:

```yaml
config:
  interrupts:
    mode: report                              # allow / report（既定）/ fail
    allow: ["Cookie の同意", "通知の許可"]      # 黙って閉じてよいダイアログ
```

- `report`（既定）: 閉じて続行し、警告として記録する。
- `allow`: 閉じて続行し、記録だけ残す（警告にしない）。
- `fail`: 閉じずに、その `do` を失敗にする。
- `allow` のリストに当たるダイアログは、モードにかかわらず警告にしない。どれに当たるかは AI が判断し、その理由を記録する。

警告は個別には通知せず、終了時の要約とレポートに出す。シナリオの結果は「合格」「警告付き合格」「不合格」の 3 つ、各ステップの結果は「合格」「不合格」「未実行」の 3 つ。

**判断後に画面が変わったら操作しない**（段階 1 で追加）: AI がスクリーンショットを見てから操作するまでに約 1 秒ある。その間にダイアログが出ると、クリックがダイアログに吸われ、文字入力が空振りした（Web 試験アプリの Cookie 同意ダイアログで実際に起きた）。操作の直前にもう一度撮り、AI が見た画面と違っていれば操作せずに撮り直して AI に聞き直す。動き続ける画面で終わらなくならないよう、1 つの `do` につき 2 回までとし、それ以降はそのまま操作する。

### 8.4 失敗したとき

- `then` が不合格 → 記録して続行する。
- `do` が実行できない（AI が `fail` を返す、操作回数の上限 `config.max_actions` を超える、エラーダイアログが出る）→ そのシナリオを打ち切る。残りのステップを「未実行」として記録し、次のシナリオへ進む。既存シナリオのセクションは続きものの手順として書かれているため（例: `sample/sample-search.yaml` の「起動 → 検索 → 検索実行 → 結果確認」）、途中から続けても後続が連鎖して失敗するだけになる。
- `config.timeout`（シナリオ全体の上限）を超えたときも、そのシナリオを打ち切る。
- `config.on_failure` で変えられる。

| 値 | 動き |
|---|---|
| `stop_scenario`（既定） | 上記のとおり |
| `next_section` | 次のセクションへ進む。セクションが互いに独立している場合用で、各セクションの前にアプリを初期化する（`config.reset` と同じ処理）。前提となる操作は `replay` で書く |
| `stop_all` | 最初の失敗で実行全体を止める |

## 9. 失敗のリアルタイム通知

エンジンは、失敗（`then` の不合格・`do` の失敗）のたびに 1 行のイベントを出す。内容はシナリオ名・セクション・ステップ・期待結果・AI の理由・AI が読み取った文字・画像のパス。秘密の値は伏せる（11.3）。出力先は標準出力と `.uiai/results/<timestamp>/events.jsonl`。

- 通知するのは失敗だけ。「未実行」と警告は個別には通知せず、終了時に要約を 1 回出す。
- `do` の失敗の通知には「残り N ステップは未実行」を含める。

| 経路 | 届く先 | 用途 |
|---|---|---|
| Claude Code のセッション（標準） | チャット。席を離れていれば、デスクトップ通知（Remote Control 接続中はスマホにも） | ふだんの実行 |
| Webhook（任意） | Slack・Teams など。URL は環境変数 `UIAI_WEBHOOK_URL` などで渡す。1 回の実行で 10 件を超えたら、以降は終了時にまとめて 1 回で送る | CI や、Claude Code を使わずに実行するとき |
| OS のデスクトップ通知（任意。`uiai run --notify`） | mac・Linux・Windows の通知センター。失敗は 1 回の実行で 5 件まで、終了時にまとめ | Claude Code なしで手元で実行するとき（段階 4 で実装。Windows・Linux は未検証） |

Claude Code のセッションでの流れ:

1. `/uiai:test` のスキルは、`uiai run` をバックグラウンドで起動する（実行中も会話を止めないため）。
2. 続けて `uiai watch --run <id>` を Monitor ツールで見張る。`watch` は失敗イベントだけを 1 行ずつ出し、実行が終わると終了する。
3. 失敗が届くたびに、Claude がチャットで知らせる。ユーザーが席を離れていそうなら、デスクトップ通知（PushNotification）も送る。
4. 実行が終わったら、レポートを要約して返す（警告もここで伝える）。

プラグインの「モニター」機能（`monitors.json` の `when: "on-skill-invoke:test"`）でも同じことができるが、仕様が experimental 扱いのため、まずは Monitor ツールを使う。Monitor ツールは非対話モード（`claude -p`）でも動いた（段階 2 で確認。届いた失敗に Claude が応答し、実行の終了後にまとめを返した）。ただし CI ではチャットの相手がいないため、通知は Webhook に任せる。

Monitor には寿命の上限があり、30 分を指定しても 10 分で切れる環境があった（段階 2 で確認）。`uiai watch` は `--timeout` で自分から少し早く終わり、続きを読むためのコマンド（`--skip <読んだイベント数>`）を出す。スキルはそれで張り直す。

## 10. AI の呼び出し

- **既定は Claude Code バックエンド**: `claude -p` を 1 プロセス起動したまま、stream-json でメッセージを送る。手元ではユーザーの Claude Code のログインで動き、API キーは要らない（CI は 6.4）。ツール無効・ユーザーのフック無効（`--tools ""`、`--setting-sources project` など）で起動する。
- **既定のモデルは haiku（決定）**。`config.model` やコマンドの引数で変えられる。計測では haiku と sonnet で判定精度の差はなかった。
- **会話が長くなる問題**: 画像は 1 枚 1,000〜1,600 トークンで、会話に溜まっていく。段階 4 の計測（14.4）では、入力の長さは応答時間にほとんど効かなかった（1,000 トークンあたり 0.44 ミリ秒。時間を決めるのは出力の長さで、1 トークンあたり 3.6 ミリ秒）。一方で、入力の総量は呼び出し回数の 2 乗で増え、120 回ほどでコンテキストの上限（20 万トークン）に届く。
  - 当初案の「セクションごとに作り直す」は、試すと逆効果だった。新しい会話の最初の応答は思考が 2〜3 倍長く（2〜4 秒）、持ち越した前のセクションの `then` を、新しい `do` の結果と取り違えて不合格にした（3 回中 2 回）。
  - そこで、**会話が大きくなったときだけ**作り直す。直前の呼び出しの入力が 5 万トークンを超えたら次のセクションの境目で、10 万トークンを超えたら次の `do` の前で作り直す（`do` の途中では作り直さない）。切り替える前に、判定待ちの `then` は古い会話で判定し切る（判定だけの呼び出し）。新しい会話には、直前 12 ステップの結果をテキストで引き継ぐ。
  - `claude -p` の起動は約 0.4 秒、終了は約 0.6 秒。作り直しは次の `do` の撮影の前に始め、古い会話は裏で閉じる。
- **秘密の値は渡さない**: プロンプトには `(password)` のようなプレースホルダーのまま渡す。AI が `input` の文字としてプレースホルダーを返したら、エンジンが実際の値に置き換えて入力する。この説明は、秘密の変数があるシナリオにだけ、実際の変数名で載せる（段階 1 で判明。説明の例 `"(password)"` を常に載せていたところ、秘密の変数がないシナリオで AI がその文字列をそのまま入力した）。
- **任意で API バックエンド**（段階 4 で実装。実際の API では未検証）: `uiai run --backend api`（または `UIAI_BACKEND=api`）で、Messages API を `ANTHROPIC_API_KEY` で直接呼ぶ（`engine/uiai/ai/api.py`）。
  - 明示したときだけ使う。`ANTHROPIC_API_KEY` があるだけで切り替えると、ほかの用途でキーを設定している人が気づかないまま従量課金で動くため。
  - 毎回の入力を自分で組み立てる。それまでの手順のテキスト（エンジンのメッセージと AI の返答）は全部送るが、画像は最新の 2 枚だけで、古いものは「もう見せていない」という一言に置き換える。入力はテキストの分しか伸びない。
  - プロンプトキャッシュの区切りを、システムプロンプトの後と「次の呼び出しでもそのまま送る部分」（画像を外した手順まで）の後に置く。
  - モデル名は Claude Code と同じ別名を使う（2026-11-12 に `claude -p --model haiku|sonnet` で確かめた。haiku は `claude-haiku-5-5`、sonnet は `claude-sonnet-5-5`）。それ以外の名前はそのまま送るので、完全なモデル ID も使える。新しいモデルが出たら、この対応表を直す必要がある（Claude Code の別名は自動で新しくなる）。
  - 思考（thinking）は指定せず、モデルの既定に任せる。Claude Code 経由とは思考の量が違う可能性があり、速さと判定の精度への影響は測っていない。
  - 標準ライブラリ（urllib）だけで呼び、依存を増やさない（環境変数のプロキシ設定も効く）。408・429・500・502・503・504・529 と接続エラーは 3 回までやり直す（`retry-after` に従う。上限 60 秒）。それ以外のエラー（400・401・403・404 など）と、URL の誤り・証明書の検証の失敗はやり直さずに実行エラーにする。やり直しを含めて 1 回の呼び出しは 120 秒まで（Claude Code 経由と同じ。少しずつ届く応答でも、この時間で打ち切る）。打ち切った通信は裏で残り、ソケットの待ち時間が切れたときに終わる（少しずつ送り続けるサーバーが相手だと残り続ける。未対応）。
  - リダイレクトには従わない（従うと、転送先の別のホストにキーを送ってしまうため）。`ANTHROPIC_BASE_URL` にユーザー名・パスワードは入れられない。エラーのメッセージに `ANTHROPIC_BASE_URL` の値は出さない（クエリなどにトークンが入っていることがあるため）。
  - 送ったモデルの ID を `result.json`（`model_id`。再判定の記録にも）とレポートに残す（別名の対応表を直した後でも、どのモデルで走らせたかが分かる）。
  - 出力の上限（`max_tokens`）は 8192。返答は JSON で 200 トークンほど（Claude Code 経由の思考は 300〜700 トークン）。出力の上限がこれより小さい古いモデルは、完全な ID を指定しても 400 で拒まれる。上限に達して途中で切れた応答と、AI が拒否した応答（`stop_reason: refusal`）は、壊れた返答として渡さずに実行エラーにする（渡すとループが「応答を解釈できない」として、アプリの不合格にしてしまう）。
  - キーの前後の空白・改行は取り除く（CI のシークレットに改行が紛れ込みやすい）。キーと `ANTHROPIC_BASE_URL` は `uiai run` の開始前（`--dry-run` を含む）に同じ検査をし、使えなければ何も始めずに終了コード 2 にする。`uiai setup` も同じ検査の結果を 1 つずつ表示する（キーがないことは失敗にしない。CI では、キーを実行の手順にだけ渡すことが多いため）。どんな失敗も、キーを伏せた `AIError` にして実行エラーとして記録する。
  - 会話を作り直す条件（入力 5 万・10 万トークン）は、Claude Code 経由と同じものがそのまま働く。
- **呼び出し回数を減らす**: 「入力欄をタップ」と「文字を打つ」を 1 回の `input` にまとめるようプロンプトで促す。試作の Web 試験アプリでは、AI が自分からまとめた実行は 19 回・27.8 秒、分けた実行は 23 回・30.9 秒だった（プロンプトで促した場合の効果は未検証）。
- **sonnet での再判定**（段階 4 で実装）: `then` が待ち時間を過ぎても不合格のとき、確定する前に別のモデル（既定 sonnet。`--rejudge-model`）が、同じ画像と `then` の文と直前の `do` の文だけで判定し直す。会話は毎回新しく作る（前の判定に引きずられないため）。sonnet が合格とすれば合格にし、判定が分かれたことを警告に残す（画面があいまいな可能性があるため）。sonnet も不合格なら、両方の理由を残して不合格にする。かかるのは不合格になりかけたときだけで、1 回 1.3〜2.0 秒。

## 11. シナリオ形式

既存のシナリオはそのまま動くようにする。仕様書は Android・iOS・Web で 3 つに分かれ、内容もずれていた（Android 版に `app.web` がない、iOS 版はリンク切れ）。`skills/test/references/scenario-schema.md` の 1 つにまとめる。

### 11.1 実行するプラットフォームの決め方

1. `/uiai:test` や `uiai run` で `platform` が指定されていれば、それに従う。
2. 指定がなければ、`app` から候補を出す。
   - オブジェクト形式: 書かれているキー（`android`・`ios`・`web`）が候補。
   - 文字列形式: `http://`・`https://` で始まるか、`.html` で終わるなら `web`。それ以外は `android` と `ios` の両方が候補（仕様上「両プラットフォームで同じ識別子」という意味のため）。
3. 候補を、いま実行できる対象（接続中の Android 端末・起動中の iOS シミュレータ。Web は常に実行できる）に絞る。
4. 1 つに決まれば、それで実行する。複数残ったら実行せず、`platform` の指定を求める（`/uiai:test` では Claude がユーザーに確認する）。`platform=all` なら、残った全部で実行する。

### 11.2 フィールド

| フィールド | 新設計での扱い |
|---|---|
| `name`、`steps`、`id`、`actions`、`do`、`then` | そのまま |
| `app` | そのまま（`android`・`ios`・`web` のキーを持つオブジェクト、または文字列）。プラットフォームの決め方は 11.1 |
| `variables`・プレースホルダー | そのまま（エンジンで解決）。秘密の値の指定を追加（11.3） |
| `replay` | そのまま（エンジンで展開。`then` はスキップ） |
| `wait` | そのまま（固定待機） |
| `strict`（各行）・`config.strict`（全体の既定） | 意味を変更: AI に一字一句の完全一致で画像を判定させる（8.2） |

| `config.timeout` | 意味はそのまま（シナリオ全体の上限、秒）。既定は 600 秒。AI 方式は 1 ステップ 3〜6 秒かかるため、書かれた値が「`do` の数 × 10 秒」より小さければ `uiai check` が警告する |

| 新規 `then.timeout`・`config.then_timeout` | `then` を待つ上限（秒、既定 5） |

| 新規 `config.on_failure` | 失敗したときの動き（8.4） |
| 新規 `config.reset` | 開始前（`next_section` では各セクションの前）に止める関連パッケージなど（試作の `reset_packages`） |

### 11.3 秘密の値

```yaml
variables:
  email: "test@example.com"
  password:
    env: TEST_PASSWORD     # 環境変数から読む（シナリオに値を書かない）
    secret: true
```

- 秘密の値は AI に渡さない（10 章）。
- `result.json`・レポート・イベント・Webhook に出る文字列からは、値を `****` に置き換える。
- `then` で秘密の変数を使うと AI が照合できないため、`uiai check` がエラーにする。
- 画面に平文で表示される値（伏せ字でない入力欄など）は、スクリーンショット経由で AI に送られる。これは防げないため、注意事項として明記する。

| sonnet での再判定 | 10 章。保存してあった画像で確かめた: 誤った不合格 2 件（取り違えによるもの）は 2 回とも合格に、本当のエラー 1 件は 2 回とも不合格のまま。受け入れ確認（`examples/acceptance/`）は 5 本とも期待どおり（遅れて出るエラーは sonnet でも不合格、+1.77 秒） |
| 並列実行 | `uiai run --parallel`。シナリオは空いた端末に割り当てる。Web 4 本: 順番に 83 秒 → 2 ブラウザで 50 秒（判定は同じ）。Android・iOS・Web の 3 本を同時に: 87 秒（それぞれの所要時間の合計は 192 秒。同時に動かした負荷で Android は単独の 59 秒から 85 秒に延びた）。起動できない端末のシナリオは、同じプラットフォームのほかの端末に回る |
| OS のデスクトップ通知 | `uiai run --notify`（9 章）。mac で osascript が正常終了することまで確認（画面に出たかは目視していない）。Linux・Windows は未検証 |
| API バックエンド | `uiai run --backend api`（10 章）。偽の応答で、送る内容（画像は最新 2 枚・キャッシュの区切り・モデル名）、使用量の集計、やり直し、エラー、シナリオ全体の実行を確かめた（単体テスト 79 件。API バックエンド 62 件・CLI 17 件。手元の HTTP サーバーへの実際の通信（リダイレクト、少しずつ届く応答を含む）も確かめた）。実際の API には、無効なキーで 1 回だけ送り、401 とそのエラー内容を正しく受け取れることまで確認した。正しいキーでの実行（モデル名が通るか、速さ、判定の精度、キャッシュの効き）は未検証 |
| 未着手 | Windows・Linux からの iOS 操作（遠隔の Mac が要るため） |

段階 4 で見つけて直したこと:

| 見つかったこと | 対応 |
|---|---|
| セクションごとに会話を作り直すと、遅くなり（呼び出しの合計が増え、最初の応答が 2〜4 秒）、判定も誤った（10 章） | 会話が大きくなったときだけ作り直し、判定待ちの `then` は古い会話で判定し切る |
| `then` の判定し直しの間は `do` の操作を実行しないが、そのことを AI に伝えていなかった。AI は「押したのに遷移しない」と受け取って押し直し、最後は `do` を失敗にした | 実行しなかった操作は、次のメッセージで「実行していない」と伝える |
| AI が送るキー名 `cmd+a` を Playwright が知らない（エラー）。`Control+a` は mac では行頭へ移るだけで全選択にならない | よく使う名前を Playwright の名前に直す。ショートカットの修飾キーは `ControlOrMeta`（mac は Meta、ほかは Control）にする |
| API バックエンドのレビューで、末尾に改行のある API キーで並列実行すると、urllib の例外にキーが載って画面に出て、シナリオが結果にも未実行にも数えられず、終了コード 0 になった（実行して再現） | キーの空白を取り除き、API の想定外の失敗はキーを伏せて `AIError` にする。実行ループは想定外の例外も実行エラーとして記録し、それでも抜けた例外は未実行として数える（終了コード 2） |
| 同じレビューで、セクションの境目で判定待ちの `then` を判定し切る間にシナリオの上限時間を超えると、エンジンが落ちることが分かった（段階 4 より前からある） | その `then` を不合格にして、残りを未実行にする |
| `uiai setup` が、`--backend api` では使わない Claude Code CLI がないと失敗にしていた | `uiai setup --backend api`（または `UIAI_BACKEND=api`）では失敗にしない |
| 再判定のモデルが判定のモデルと同じかを名前の文字列で比べていたため、`--backend api --model claude-sonnet-5-5` と既定の `--rejudge-model sonnet` では、同じモデルで判定し直していた | `--backend api` では別名を完全な ID に直してから比べる。Claude Code の別名は自動で新しいモデルに移るため、`claude-code` では同じ名前だけを同じモデルとみなす（完全な ID と別名を混ぜると、同じモデルで判定し直すことがある） |
| レポートを書けなかったとき（ディスクがいっぱいなど）の扱いが決まっていなかった | 結果はそのまま数え（`on_failure: stop_all` も効く）、実行は最後までできなかったとして終了コード 2 にする。理由は最後の一覧と `summary.md` に出す |
| 想定外の例外を実行エラーとして記録するようにしたことで、原因の場所（トレースバック）が残らなくなった | トレースバックを標準エラー出力に出す（秘密の値は伏せる） |
| ディスクがいっぱいで `events.jsonl` や `summary.md` を書けないと、`uiai run` が終了コード 1（不合格の意味）で落ち、まとめも出なかった（段階 4 より前からある） | `events.jsonl` は書けないイベントだけを抜かし（空きが戻れば、実行の終わりも書かれる）、標準エラー出力に一度だけ知らせる（通知は続ける）。`summary.md` を書けなくても最後の一覧は出し、理由をイベントに残して終了コード 2 にする |
| AI の返答に UTF-8 にできない文字（対になっていないサロゲート）が入ると、記録や通知で例外になって実行が落ちていた（段階 4 より前からある） | 記録はその文字を置き換えて書く。通知の失敗は標準エラー出力に出して続ける |
| 長いシナリオで、AI が「検索欄の後ろに「タワー」を追加で入力」を「東京タワー」と打ち直し、全選択もできずに操作回数の上限で止まった | 計測用のシナリオからこの手順を外した（キー名は上で直した） |

計測から分かったこと:

- AI の応答時間は出力の長さでほぼ決まる（Web の 124 回で回帰。`api_s = 0.52 + 0.0036 × 出力トークン + 0.00044 × 入力千トークン`、決定係数 0.89）。7 万トークンの入力でも +0.03 秒
- 出力の多くは思考（thinking）で、JSON 本体は 150〜250 トークン。新しい会話で、前の手順の履歴と判定待ちの `then` が一緒に来ると、思考が 300〜700 トークンに増えた
- `--effort low` で出力は 3 割ほど減った（平均 599 → 427 トークン）が、`alwaysThinkingEnabled: false` や `MAX_THINKING_TOKENS=0` ではほとんど減らなかった（2 回ずつ試しただけ）。判定の精度への影響を測っていないため、変えていない

## 15. リスクと未検証事項

| 項目 | 内容・対策 |
|---|---|
| 判定の揺れ | 同じ画面でも実行ごとに判定が変わる可能性がある。段階 1 では Web・Android とも 5 回続けて判定が一致した（14.1）。回数が少なく、長いシナリオや別のアプリでは未計測。誤った不合格は sonnet の再判定で減らす（10 章）が、誤った合格は減らせない |
| 誤った合格 | AI が楽観的に合格とする、または迂回して達成してしまう可能性がある。証拠画像と読み取った文字を残し、割り込み・再起動・何もしない・遠回りを警告として出す（8.3） |
| strict の限界 | 見た目で区別できない文字（空白の数・半角と全角の一部）は判定できない。省略・伏せ字・画面外の文字は「判定できない」として不合格にする。試験では誤りは安全側（不一致と判定）だったが、件数は少ない |
| 否定形の `then` | 観察時間（既定 2 秒）より遅れて出るエラーは見逃す。必要なら `then.observe` を延ばす |
| 撮影できない画面 | Android の `FLAG_SECURE` の画面は真っ黒になる可能性が高い（未検証）。画像方式では判定できない |
| 画面にない対象 | 座標だけを答えさせる試験では、存在しない対象にも座標を返した。見つからないときはスクロールか `fail` を選ぶようプロンプトで明示し、タップ後に画面が変わらなければ AI に伝える |
| 長いシナリオ | 会話が 5 万トークンを超えたら作り直す（10 章）。84 ステップ・呼び出し 49 回までは、序盤と終盤で 1 ステップの時間が変わらないことを確かめた（14.4）。作り直した直後の判定が揺れる可能性は残る（切り替えは 1 回の実行で 0〜1 回しか起きておらず、件数が少ない） |
| 端末の負荷 | Android 設定アプリのシナリオが 1 度だけ 94.7 秒かかった（通常は 40〜50 秒）。撮影の待ちが 1 回 2〜10 秒に延びていた（取得回数と時間から、1 枚あたり約 2 秒）。直後のエミュレータは負荷平均 9.4・スワップ使用 1GB で、負荷が下がってから走らせ直すと 43.5 秒だった。エミュレータの負荷が原因の可能性が高い（重かった最中の撮影時間は測っていない）。iOS シミュレータと同時に動かすと、Android の設定アプリが応答しなくなったこともある（14.3） |
| 判断後の画面変化 | 動き続ける画面では、判断後の画面変化の検出（8.3）が毎回働き、1 つの `do` につき最大 2 回撮り直す分だけ時間が増える |
| iOS | シミュレータの設定アプリでのみ確認（14.3）。実機は未対応。ASCII 以外の文字は入力できない。AXe は v2.0.3 で確認しており、オプション（`--tap-style` など）が版で変わると動かなくなる。Windows・Linux からは Mac か実機の準備が必要 |
| Android の日本語入力 | uiautomator2 でクリップボード経由で入力する（7 章）。端末のクリップボードを上書きし、Android の版によっては通知が出る。Android 16 のエミュレータ（Gboard）でのみ確認。実機・ほかのキーボード・パスワード欄は未検証 |
| Windows | 文字コード・`claude` の起動・`bin/uiai.cmd`（PowerShell）と `bin/uiai`（Git Bash）からの実行は未検証 |
| CI | `claude -p` の CI での認証（長期トークン）、`uiai setup --with-deps` での Linux のブラウザの準備、CI 上のエミュレータの速さは未検証（手順は `docs/ci/`） |
| 見張りの寿命 | Monitor の寿命の上限は環境で違う（10 分の例あり）。`uiai watch` を 9 分で区切って張り直すが、張り直しの間に Claude が別の作業をしていると、失敗の通知が遅れる |
| 実機 | 計測はエミュレータのみ。USB 接続の実機では撮影速度が変わる可能性がある |
| Claude Code CLI への依存 | stream-json や画像入力の仕様が変わる可能性がある。逃げ道として API バックエンド（`--backend api`）を用意した（実際の API では未検証）。思考（thinking）の量は `claude -p` の側で決まり、`--effort low` でも少し減るだけで止められなかった |
| 画面内容の送信 | スクリーンショットは Anthropic の API に送られる（現行方式も同じ）。画面に平文で出る秘密の値も含まれる。機密情報を含むアプリでの利用は注意事項として明記する |
| コスト | 1 回の入力は画像込みで 1,500〜2,000 トークン程度、1 シナリオで 10〜25 回。会話に画像が溜まるため、入力の総量は 50 ステップのシナリオで 108〜152 万トークン（大半はキャッシュの読み出し）。料金は未試算 |
| 小さい対象・特殊な画面 | 48dp 未満の対象や Canvas・ゲーム画面は未検証 |
